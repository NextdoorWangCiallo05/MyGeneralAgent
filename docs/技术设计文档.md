# 通用对话 + 工具调用 Agent 应用 — 技术设计文档

> 版本：v2.2
> 定位：面向开发团队的详细技术设计（Technical Design Document, TDD）
> 技术栈：Next.js（React）前端 + Python（FastAPI）后端
> 关键决策：LLM 采用 **DeepSeek（`deepseek-flash`）**；支持**多用户注册 / 登录 / 找回密码**；沙箱采用**受限子进程 + 开关**；接入 **RAG**

## 1. 概述

### 1.1 项目背景
构建一个通用对话式 Agent 应用，用户以自然语言提出需求，Agent 能够自主调用外部工具（联网搜索、网页抓取、计算、文件读写、知识库检索等）完成多步骤任务，并通过流式方式实时反馈推理与执行过程。

### 1.2 目标
- **对话能力**：支持多轮上下文对话，具备长期记忆与 RAG 知识检索。
- **工具调用**：基于 DeepSeek Function Calling 自主规划与调用工具。
- **过程可见**：前端实时展示"思考 → 调用工具 → 观察结果 → 回答"的完整链路。
- **多用户**：支持用户注册 / 登录 / 找回密码，会话与数据严格按用户隔离。
- **安全可控**：提供沙箱执行开关；DeepSeek API-Key 由管理员统一配置。
- **可扩展**：工具、模型、记忆后端均可插拔替换。

### 1.3 范围
| 纳入范围 | 不在本期范围 |
|---------|-------------|
| 单 Agent（ReAct）核心循环 | 多 Agent 协作编排 |
| 工具注册与调用 + 沙箱开关 | 复杂 DAG 工作流引擎 |
| 多用户注册 / 登录 / 找回密码 / 会话隔离 | 多模态（图像/语音） |
| DeepSeek LLM（`deepseek-flash`，OpenAI 兼容） | 自主训练 / 微调模型 |
| RAG 知识库检索 | 企业级 RBAC 细粒度权限 |
| 会话持久化 + 流式输出 | 计费 / 支付体系 |
| 管理员配置 API-Key | |
| 可观测性与成本统计 | |

### 1.4 术语
| 术语 | 说明 |
|------|------|
| ReAct | Reason + Act，推理与行动交替的 Agent 范式 |
| Tool / Function Calling | LLM 输出结构化工具调用指令的能力 |
| SSE | Server-Sent Events，服务器单向流式推送 |
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| Turn | 一轮"用户输入 → Agent 完整响应"的过程 |

## 4. 核心模块设计

### 4.1 Agent Core（ReAct 循环）

**职责**：驱动"推理 → 调用工具 → 观察 → 再推理"的循环，直至产出最终答案。

**伪代码流程**：
```
async def run(session_id, user_input) -> AsyncIterator[Event]:
    msgs = memory.build_context(session_id, user_input)
    for step in range(MAX_STEPS):                 # 最大轮次保护
        resp = await llm.chat(msgs, tools=registry.schemas())
        if resp.has_tool_calls:
            for call in resp.tool_calls:
                yield ToolCallEvent(call.name, call.args)      # 通知前端
                result = await registry.execute(call)          # 执行工具
                yield ToolResultEvent(call.name, result)       # 通知前端
                msgs.append(tool_message(call.id, result))
            continue
        else:
            yield TextDelta(resp.content)          # 流式吐出正文
            break
    memory.persist(session_id, msgs)               # 落库
    yield DoneEvent(usage=resp.usage)              # 结束事件
```

**关键控制点**：
- `MAX_STEPS`：硬性上限，默认 10，防止无限循环。
- **单步超时**：每次 LLM 调用与工具执行均设超时。
- **终止条件**：无工具调用 / 达到最大轮次 / 用户中断 / 异常。
- **中断机制**：前端"停止"按钮 → 后端取消任务（asyncio Task cancel）。

**状态机**：
```
IDLE → THINKING → (TOOL_CALL → OBSERVING → THINKING)* → RESPONDING → DONE
                      ↓ 异常/超时
                    ERROR
```

### 4.2 Tool System（工具系统）

**职责**：提供工具的注册、schema 生成、执行与隔离。

**工具定义结构**：
```python
class Tool:
    name: str                      # 唯一标识，如 "web_search"
    description: str               # 给 LLM 看的能力描述（决定选对与否）
    parameters: dict               # JSON Schema
    handler: Callable              # 实际执行函数
    requires_confirmation: bool    # 是否需人工确认（副作用类）
    timeout: int = 30              # 执行超时（秒）
    readonly: bool = True          # 是否只读
```

**ToolRegistry 职责**：
- 注册/注销工具
- 导出 OpenAI 兼容的 `tools` 参数（JSON Schema 数组）
- 参数校验（调用前用 JSON Schema 校验 LLM 给的参数）
- 分发执行、超时控制、错误包装
- 权限与确认校验

**内置工具规划**：
| 工具 | 能力 | 只读 | 需确认 | 状态 |
|------|------|------|--------|------|
| `calculator` | 数学计算 | 是 | 否 | M1 已实现 |
| `web_search` | 联网搜索实时信息（后端可插拔） | 是 | 否 | M3 已实现，M3 续完成后端抽象（`app/search/`：Bing / DuckDuckGo / Tavily / Serper / Brave / SearXNG） |
| `fetch_url` | 抓取网页正文 | 是 | 否 | M3 已实现 |
| `read_file` | 读取沙箱内文件 | 是 | 否 | M3 已实现 |
| `write_file` | 写入沙箱内文件 | 否 | 是 | M3 已实现 |
| `python_exec` | 受限子进程执行 Python | 否 | 是 | M3 已实现 |
| `knowledge_search` | 知识库向量检索 | 是 | 否 | M4 已实现（须启用嵌入后端且本人有已向量化分块，否则 schema 不下发） |
| `read_attachment` | 分段 / 关键词读取本会话附件正文 | 是 | 否 | M4 续已实现（会话无附件时 schema 不下发） |

**执行隔离**：文件类工具限定在沙箱根目录内，做路径校验（防 `../` 逃逸）；代码执行类本期用「受限子进程」承载（禁止 `shell=True`、参数以列表传递、`-I -S` 启动解释器），不裸跑系统命令。

**schema 裁剪**：`ToolRegistry.schemas_for(sandbox_enabled=..., knowledge_enabled=..., attachments_enabled=...)`
按运行环境导出可用工具。沙箱关闭时，沙箱类工具的 schema **不下发给模型**；
知识库 / 附件类工具（`knowledge_search` / `read_attachment`）同样按会话实际情况门控，
从源头避免「模型编造出不可用的工具调用」。

**搜索后端抽象（`app/search/`）**：`web_search` 不直接绑定任何一家搜索服务，而是依赖
`SearchBackend` 协议与 `PRESETS` 预设表；配置优先级与 LLM 厂商一致（**后台配置 > 环境变量 > 预设**），
默认 `auto` 在免密钥后端（Bing → DuckDuckGo）间自动回退，全部失败时把可执行的下一步交还给模型。
新增一家搜索服务 = 一个实现类 + 一条预设，工具定义、提示词与前端均无需改动（细节见 README「联网搜索」）。

### 4.3 Memory（记忆管理）

| 类型 | 存储内容 | 存储位置 | 生命周期 |
|------|---------|---------|---------|
| 短期记忆 | 当前会话消息列表 | messages 表 | 会话级 |
| 工作记忆 | 循环中间态 messages | 内存 | 单次请求 |
| 长期记忆 | 用户偏好/知识 | pgvector | 跨会话 |
| 摘要记忆 | 历史对话摘要 | sessions.summary | 持久 |

**上下文组装策略（build_context）**：
```
[System Prompt]
[长期记忆检索结果 (RAG top-k)]
[历史对话摘要 (summary)]
[最近 N 轮完整对话]
[本轮用户输入]
```

**压缩策略**：当 token 数超过阈值（如模型上下文 70%）时，将较早的对话用 LLM 摘要成一段文字，替换原始消息，保留最近 N 轮完整对话。

> **实现现状（M4，已完成）**：落地于 `app/core/summary.py`，`plan_context()` 判断是否需要压缩并返回
> `(summary, keep_from)`；摘要写入 `sessions.summary`，进度记录在 `sessions.summary_upto_seq`
> （`-1` 表示未压缩过），因此**不会重复摘要**。配置项：`SUMMARY_TRIGGER_TOKENS`（默认 6000）、
> `SUMMARY_KEEP_TURNS`（默认 6 轮）、`SUMMARY_MIN_NEW_TOKENS`（默认 400，增量不足则跳过）。
> 摘要失败时不阻塞本轮对话，退化为「本轮不压缩」。

### 4.4 LLM Client（DeepSeek 接入层）

**目的**：封装 DeepSeek API 调用，统一输入输出，并预留扩展能力。

```python
class LLMClient(Protocol):
    async def chat(self, messages, tools, stream=True) -> AsyncIterator[Chunk]: ...
```

- **主供应商为 DeepSeek**，默认模型 **`deepseek-flash`**，采用 **OpenAI 兼容协议**对接 `/chat/completions`
- **模型名可配置**（`system_config.default_model`），无需改代码即可切换模型
- **API-Key 由管理员在后台配置**，加密存储于数据库，运行时动态读取，**绝不下发前端**
- 统一 `messages` / `tools` 格式（OpenAI 兼容格式）
- 统一返回：文本增量、工具调用、token 用量、结束原因
- 内置重试（指数退避）、超时、降级
- 预留适配器接口，未来可平滑接入其他 OpenAI 兼容模型

### 4.5 Session Store（会话存储）

- 会话元信息（标题、创建时间、模型、参数、沙箱开关）
- 消息序列（role、content、tool_calls、tool_results、token 用量）
- 支持软删除、分页加载

### 4.6 Auth（用户与鉴权）

**职责**：用户注册、登录、找回密码、身份认证与权限控制。

- **注册**：用户名 / 邮箱 + 密码（`bcrypt` / `argon2` 加盐哈希存储）
- **登录**：校验凭证 → 签发 **JWT Access Token**（可选 Refresh Token）
- **找回密码**：
  - `忘记密码`：按邮箱查询用户 → 生成**一次性重置令牌**（仅存哈希、限时 30 分钟）→ 邮件发送重置链接
  - `重置密码`：校验令牌有效性 → 更新密码 → 令牌置为已用 → 使旧会话 Token 失效
  - 无论邮箱是否存在均返回相同响应，**防止用户枚举**
- **鉴权**：FastAPI 依赖注入解析 Token，注入 `current_user`
- **角色**：`user` / `admin` 两级；管理员接口强制校验角色
- **隔离**：所有数据查询强制携带 `user_id` 条件，杜绝越权

### 4.7 RAG Pipeline（检索增强）

**职责**：将用户知识库文档向量化，并在对话时检索注入上下文。

- **写入流程**：文档上传 → 解析（PDF / Markdown / TXT）→ 分块（chunk + overlap）→ 向量化 → 存入 pgvector
- **检索流程**：用户问题 → 向量化 → 相似度检索 top-k →（可选重排）→ 注入上下文
- **触发方式**：`knowledge_search` 工具供 Agent 主动调用；或对话前预检索注入
- **嵌入模型**：选用兼容的中文友好开源模型（如 BGE 系列）或第三方 embedding API；**向量维度需与 `embeddings` 表定义保持一致**
- **多租户**：向量检索同样按 `user_id` 过滤，用户间知识库隔离

> **实现现状（M4，已完成）**：
> - **链路已闭环**：文档上传（txt / md / markdown / pdf）→ 解析（`app/core/document_parser.py`）→
>   分块（`app/core/chunking.py`，800 字 / 100 字重叠）→ **向量化**（`app/core/embedding.py`）→
>   写入 `embeddings` 表；列表 / 分块预览 / 删除 / **重建索引** / **检索调试**接口齐备，
>   前端 `/knowledge` 页面提供「补齐索引 / 全量重算」与「问句试检索」面板；
> - **向量存储偏离原设计**：当前部署为 **MySQL 8**，无原生向量类型且不可用 pgvector，
>   因此 `embeddings.embedding` 以 **JSON 文本**存储向量，检索使用**应用层暴力余弦相似度**
>   （`app/core/retriever.py`，装有 numpy 时走矩阵乘法，缺失时回退纯 Python）；
>   数据量增长后可平滑替换为 pgvector / 独立向量库（只需改这一列与检索实现）；
> - **嵌入后端可插拔**：`EMBEDDING_BACKEND=hash | local | none`。
>   `hash`（默认）用字符 2/3-gram 做 **blake2b** 哈希向量 + L2 归一化，零依赖即可跑通全链路，
>   但只有字面匹配能力；`local` 用 `sentence-transformers` + `BAAI/bge-small-zh-v1.5`
>   （离线、CPU 可跑、首次下载约 100 MB，依赖见 `requirements-ml.txt`）提供语义泛化；
>   `none` 关闭向量化，此时 `knowledge_search` 不下发给模型。
>   哈希函数刻意不用 crc32：短中文串下其雪崩性差，256/512 维时碰撞噪声会淹没真实匹配；
> - **后端切换需重建索引**：不同后端向量不在同一空间，检索按维度一致性过滤旧向量，
>   旧数据不会产生错误命中但会暂时检索不到，须执行 `POST /knowledge/reindex?force=true`；
> - **门控**：仅当嵌入后端可用**且**当前用户存在已向量化分块时才下发 `knowledge_search`
>   的 schema（`Agent._knowledge_enabled`），与沙箱的「全局总闸 + 会话开关」同为 fail-closed 思路；
>   单次检索上限 `KNOWLEDGE_SEARCH_MAX_CHUNKS`（2000 块）、阈值 `KNOWLEDGE_SEARCH_MIN_SCORE`（0.05），
>   每个片段回喂前截断到 400 字。

### 4.8 Sandbox（沙箱执行）

**职责**：为文件 / 代码类工具提供隔离执行环境，并提供开关控制。

- **开关设计**：
  - **全局开关**：管理员在后台统一启停
  - **会话级开关**：用户在会话内单独控制
  - **关闭时**：禁用文件 / 代码类工具，仅保留只读与联网类工具
- **隔离方式**：
  - **本期采用「受限子进程」**：受限子进程 + 目录白名单 + 资源（时间 / 内存）限制
  - 后续可升级为独立容器（Docker / Firecracker），限制 CPU / 内存 / 网络 / 超时
- **受限进程约束**：
  - 每次执行使用独立临时工作目录，仅允许访问沙箱根目录
  - 禁止 `shell=True`，参数以列表方式传递，杜绝命令注入
  - 设置执行超时（超时强制 kill）与内存 / 输出大小上限
  - 默认禁止外网访问（可按需放开）
- **路径安全**：所有文件操作限定在用户独立沙箱根目录，规范化路径后拒绝 `../` 逃逸
- **资源限制**：执行超时、内存上限、外网访问均可配置

**本期实现（M3，`app/tools/sandbox.py`）**：

- **双重门控**：沙箱可用 = 管理员全局总闸（`sandbox_global_enabled`，默认 false，fail-closed）
  **且** 会话级开关（随 `POST /chat` 的 `sandbox_enabled` 下发）；任一未开则沙箱类工具不下发给模型；
- **路径白名单**：`resolve_path()` 为文件类工具唯一入口，规范化后校验，拒绝空串、`\x00`、绝对路径、
  Windows 驱动器前缀、`..` 与符号链接逃逸；用户目录为 `SANDBOX_ROOT/<user_id>`，跨用户不可达；
- **受限子进程**：`asyncio.create_subprocess_exec` + 参数列表（无 shell）+ `-I -S`；
  每次执行使用独立临时目录并清理；`HOME` / `TEMP` 等指向临时目录，环境变量按白名单最小继承；
  执行超时强制 kill、单路输出截断、虚拟内存上限（`resource` 仅 Unix 生效）；
- **取消安全**：上层取消（用户停止生成 / 确认超时）时通过 `except BaseException` 回收子进程。

**人工确认（M3，`app/core/confirmations.py`）**：

- Agent 遇到 `requires_confirmation` 工具时，**先 `create()` 登记**再下发 `tool_confirm`，
  随后 `await` 该 Future —— 规避「用户秒点确认，而 Agent 尚未开始等待」的竞态；
- 前端调用 `POST /api/v1/chat/confirm` 由 `resolve()` 唤醒，SSE 流在此期间保持打开；
- 超时（`TOOL_CONFIRM_TIMEOUT`）、连接中断、用户停止生成一律**按拒绝处理**，绝不默认放行；
- 待确认表保存在进程内，多实例部署需改为 Redis。

### 4.9 对话附件（Chat Attachment）

**职责**：让用户在聊天输入框把文件随消息一起发给模型，Agent 能直接读取文件内容作答。

- **上传与发送分离**：前端**选择即上传**（`POST /attachments` 拿到 `attachment_id`），
  发送时只在 `POST /chat` 的 `attachment_ids` 里带上 id，避免消息请求体里塞大文件；
- **解析复用 RAG 的文档解析器**：`app/core/document_parser.py`（UTF-8-sig / UTF-8 / GB18030 编码探测、PDF 提取、
  扩展名 → 类型判定），因此支持格式与知识库一致，错误码（`UNSUPPORTED_DOCUMENT` / `DOCUMENT_TOO_LARGE` /
  `DOCUMENT_PARSE_ERROR`）也同源；支持 txt / md / markdown / log / **csv / json** / pdf，
  **白名单（`ATTACHMENT_ALLOWED_TYPES`）与解析器类型集必须一致**——曾出现「允许 json 但解析器不认 json」
  导致上传必失败的问题，现由测试（`test_upload_accepts_json_attachment`）兜住；PDF 依赖 `pypdf`，
  未安装时按 `UNSUPPORTED_DOCUMENT` 明确提示安装命令，而非静默失败；
- **存储分离**：解析后的正文存 `attachments` 表，`messages.attachments` 只存元数据快照
  （id / filename / file_type / size_bytes / char_count），避免大文本撑大消息表；
- **上下文注入（会话级）**：附件绑定会话后是**会话级资源**——正文渲染为带序号与边界的文本块，
  注入 **system 提示的「本会话文件」区**，因此**整个会话的每一轮都能看到**，不需要在后续轮次重新上传
  或重新触发工具调用。放在 system 的稳定位置还有一个好处：顺应前缀缓存（KV cache），
  且历史被摘要压缩（4.8）后附件正文仍在场。用户消息里只在当轮带附件时追加一行
  「（本轮新上传：xxx.md；正文见上方「本会话文件」区）」，不重复正文：

  ```
  【附件 1】manual.md（markdown, 12.3 KB, 4210 字, id=att-uuid-1）
  <附件内容>
  ...（超过 ATTACHMENT_MAX_CHARS 截断）
  </附件内容>
  ```

- **双层注入预算**：单文件 `ATTACHMENT_MAX_CHARS`（默认 **10 万字符**，2026-10 由 2 万上调）——
  上限过小会把长文档的后半段**悄悄截掉**（模型看不到却照样自信作答），
  截断时会在正文末尾写明「此处仅提供前 N 字」，让模型知道自己拿到的是节选；
  全会话 `ATTACHMENT_CONTEXT_MAX_CHARS`（默认 **10 万字符**）——预算按**最新文件优先**分配，
  放不下的文件不展开正文（低于 `MIN_EXPAND_BUDGET` 时不展开碎片），只输出一行
  「（未整体展开：会话内附件总量已超出注入预算，需要内容时用 read_attachment(attachment_id="...") 读取）」，
  模型据此按需取用；因此上限是配置项而非硬编码：带超大文件时调小 `ATTACHMENT_MAX_PER_MESSAGE`
  或 `ATTACHMENT_CONTEXT_MAX_CHARS`（自动降级为工具读取），也可改走知识库检索（4.7）按片段喂。
  回归用例：`test_chat_injects_attachment_longer_than_previous_limit`、
  `test_session_files_remain_available_in_later_turns`、`test_session_file_budget_demotes_files_to_tool`；
- **按需读取工具 `read_attachment`**（`app/tools/attachments.py`）：对**本会话附件**分段读取，
  支持 `offset` / `limit` 分段与 `keyword` 命中定位（返回命中处的上下文窗口）；
  会话里没有任何附件时 schema 不下发（`attachments_enabled` 门控）；
  工具内校验 `user_id` 归属，且**已绑定到其他会话的附件拒绝读取**——否则猜到 id 就能跨会话翻文件。
  回归用例：`tests/test_attachment_tool.py`；
- **生命周期与清理**：上传后 `message_id` 为空（未发送）→ 随消息发出时绑定并豁免清理；
  始终未发送的附件超过 `ATTACHMENT_TTL_SECONDS` 由上传路径顺带清理（节流，见 `_purge_stale`）；
- **重新生成**：不依赖前端回传——`_truncate_last_turn` 从库中恢复该条用户消息的附件 id 后重新注入，
  附件已被删除则跳过并记录日志；
- **隔离**：上传 / 读取 / 删除 / 随消息发送全部校验 `user_id`，跨用户一律 404（fail-closed）。

> **本期取舍**：不做多模态文件上传（图片 / 语音），也不做「附件即知识库」的自动入库——
> 附件在**会话内**长期可用（system 注入 + `read_attachment` 按需读取），但**不跨会话**：
> 新会话看不到旧会话的附件；需要长期 / 跨会话检索请走知识库（4.7）。

### 6.2 核心接口：`POST /api/v1/chat`

**请求头**：`Authorization: Bearer <JWT>`

**请求体**：
```json
{
  "session_id": "uuid",
  "message": "帮我查一下今天北京天气并总结",
  "stream": true,
  "model": "deepseek-flash",
  "tools": ["web_search", "calculator"],
  "sandbox_enabled": false,
  "attachment_ids": ["att-uuid-1"]
}
```

> `attachment_ids`（可选）：先行 `POST /attachments` 上传得到的附件 id 列表。
> 服务端在**创建会话之前**校验数量（`ATTACHMENT_MAX_PER_MESSAGE`）与归属（缺失 / 越权 → 404），
> 提交后把附件绑定到该条消息与所在会话：正文渲染为 `【附件 N】文件名` + `<附件内容>` 文本块，
> 注入 system 的「本会话文件」区随请求下发（**本会话后续每一轮同样可见**）；
> 重新生成时按消息中的快照自动恢复，无需前端回传。

**响应（SSE 事件流）**：
```
event: start
data: {"message_id": "...", "session_id": "..."}

event: thinking
data: {"delta": "我需要先搜索..."}

event: tool_call
data: {"id": "call_1", "name": "web_search", "args": {"q": "北京天气"}}

event: tool_result
data: {"id": "call_1", "status": "success", "summary": "获取 5 条结果"}

event: text
data: {"delta": "今天北京..."}

event: usage
data: {"prompt_tokens": 320, "completion_tokens": 128}

event: done
data: {"finish_reason": "stop"}

event: error
data: {"code": "TOOL_TIMEOUT", "message": "..."}
```

**事件类型定义**：
| event | 含义 |
|-------|------|
| `start` | 开始本次响应 |
| `thinking` | 推理文本增量（可选展示） |
| `tool_call` | 发起工具调用 |
| `tool_confirm` | 该工具需人工确认；流挂起等待 `POST /chat/confirm`（`expires_in` 为等待秒数） |
| `tool_result` | 工具执行结果（`status`：`success` / `error` / `timeout` / `rejected`） |
| `text` | 最终回答文本增量 |
| `usage` | token 用量 |
| `done` | 本轮结束 |
| `error` | 异常 |

### 6.3 错误码
| code | HTTP | 说明 |
|------|------|------|
| `UNAUTHORIZED` | 401 | 未认证 / Token 无效 |
| `FORBIDDEN` | 403 | 无权限（如非管理员访问管理接口） |
| `INVALID_CREDENTIALS` | 401 | 用户名或密码错误 |
| `USER_EXISTS` | 409 | 用户名 / 邮箱已存在 |
| `INVALID_RESET_TOKEN` | 400 | 重置令牌无效 / 已过期 / 已使用 |
| `RATE_LIMITED` | 429 | 触发限流 |
| `SESSION_NOT_FOUND` | 404 | 会话不存在 |
| `CONFIRMATION_NOT_FOUND` | 409 | 确认请求已失效（已超时 / 已处理 / 会话不匹配） |
| `API_KEY_NOT_CONFIGURED` | 503 | 管理员尚未配置 DeepSeek API-Key |
| `ATTACHMENT_NOT_FOUND` | 404 | 附件不存在或不属于当前用户（发送不存在的附件 id 同样返回该错误） |
| `TOO_MANY_ATTACHMENTS` | 400 | 单条消息携带的附件数超过 `ATTACHMENT_MAX_PER_MESSAGE` |
| `SANDBOX_DISABLED` | 200(流内) | 沙箱关闭，文件 / 代码工具不可用 |
| `TOOL_TIMEOUT` | 200(流内) | 工具超时 |
| `LLM_ERROR` | 200(流内) | 模型调用失败 |
| `MAX_STEPS_EXCEEDED` | 200(流内) | 超过最大轮次 |
| `INTERNAL_ERROR` | 500 | 未捕获异常兜底（详见下方「500 必须自己回」） |

**500 必须自己回（否则前端只会说「后端没启动」）**：未捕获异常若直接冒泡，Starlette 会用最外层的
ServerErrorMiddleware 生成 `text/plain` 的 `Internal Server Error`，而这个响应**不经过 CORSMiddleware**，
浏览器因缺少 `Access-Control-Allow-Origin` 读不到任何 body，前端 `fetch` 直接 reject，
只能显示「无法连接后端服务，请确认后端已启动」——把「后端有 500 级 bug」误报成「后端没启动」，
排查方向被彻底带偏（曾真实发生：长 PDF 入库报 `DataError` → 用户以为后端挂了）。

因此 `RequestContextMiddleware`（位于 CORSMiddleware 内侧）捕获所有未捕获异常：
先按 `request_id` 记下 traceback，再返回标准信封 `{"code": "INTERNAL_ERROR", "message": ...}`，
这样响应重新经过 CORS 中间件，前端能拿到可读原因。回归用例：
`test_unhandled_error_returns_json_envelope_with_cors`。

**大文本列一律用 `LONGTEXT`**：MySQL 的 `TEXT` 上限是 65535 **字节**（不是字符），
下面三列都可能超限，且超限后都是「数据库报错 → 500」而非可读的校验错误：

- `attachments.text`：1 MB 的 PDF 就能抽出 4.9 万汉字 ≈ 147 KB（真实踩过）；
- `messages.content`：用户单条消息上限 3.2 万字符，**中文 ≈ 96 KB 已经越界**；
  工具结果也原样入库（`fetch_url` 单次最多 1 MB、`read_file` 256 KB、`python_exec` 64 KB）；
- `embeddings.embedding`：3072 维向量的 JSON ≈ 60 KB，已贴着上限。
模型侧统一走 `app.models.LONG_TEXT`（`Text().with_variant(mysql.LONGTEXT(), "mysql")`，
SQLite 等方言退化为 `TEXT`），迁移 `0007_long_text_columns.py` 对齐存量库；
文件名则在入库前用 `ensure_filename_length` 卡 255 字符，避免同类「数据库报错 → 500」。

## 7. 前端设计

### 7.1 页面路由（Next.js App Router）
```
/app
 ├── /login              登录页
 ├── /register           注册页
 ├── /forgot-password    忘记密码（提交邮箱发送重置邮件）
 ├── /reset-password     重置密码（凭邮件令牌设置新密码）
 ├── /(main)             主应用（需登录）
 │    ├── 侧边栏：会话列表、新建会话、用户信息、登出
 │    ├── 主区：消息流（用户气泡 / Agent 气泡 / 工具调用卡片）
 │    ├── 输入区：多行输入、发送、停止生成、沙箱开关
 │    └── /knowledge     知识库管理（文档上传 / 列表 / 删除）
 └── /admin              管理后台（仅 admin 角色）
      ├── DeepSeek API-Key / 默认模型配置
      ├── 沙箱全局开关
      └── 用户列表管理
```

### 7.2 关键实现点
- **SSE 消费**：用 `EventSource` 或 `fetch + ReadableStream`（后者支持 POST）。
- **流式渲染**：`text` 事件累积追加，打字机效果；`tool_call/tool_result` 渲染为可折叠卡片。
- **工具过程可视化**：显示"🔍 正在搜索：xxx"、"✅ 已获取 5 条结果"，让用户感知进度。
- **停止生成**：调用 `/chat/stop`，中断本地流。
- **认证**：登录后保存 JWT（推荐 httpOnly Cookie + 内存），请求头带 `Authorization: Bearer`；捕获 401 自动跳登录。
- **路由保护**：`/(main)` 需登录；`/admin` 需 admin 角色（middleware 校验）。
- **沙箱开关**：输入区开关随会话保存，调用 `PATCH /sessions/{id}`；开关是否可用由 `GET /config`
  的 `sandbox_global_enabled` 决定，全局关闭时置灰并提示原因。
- **人工确认**：收到 `tool_confirm` 时把卡片切换为「待确认」并**强制展开参数**、显示剩余秒数，
  用户点击后调用 `POST /chat/confirm`；拒绝 / 超时由后端回 `tool_result(status=rejected)`。
- **附件（v2.2）**：`ChatComposer` 点「＋」或拖拽文件即上传，chip 展示扩展名 / 文件名 / 大小与移除按钮，
  上传中 / 失败有独立态且不参与发送；**失败时把后端返回的原因直接写在输入框下方**（不只放在 tooltip 里，
  否则用户只看到「失败」不知道原因）；发送只传 `attachment_ids`。用户气泡内以卡片列出附件，
  点击**懒加载**原文（`GET /attachments/{id}`，每个附件只拉一次）。
- **状态管理**：推荐 Zustand / Redux，按 session 隔离消息流；用 SWR / React Query 拉取会话与知识库。
- **Markdown/代码高亮**：`react-markdown` + `shiki`/`highlight.js`。

## 8. 关键技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| LLM 供应商 | **DeepSeek**（OpenAI 兼容） | 成本低、中文强、原生 Function Calling |
| LLM 默认模型 | **`deepseek-flash`** | 速度快、成本低；模型名可配置切换 |
| API-Key 管理 | 管理员后台配置 + 加密存储 | 集中管控、不泄露前端 |
| 用户体系 | **多用户**，JWT 鉴权，含**找回密码** | 支持注册登录、自助找回、数据隔离 |
| 找回密码 | 邮件一次性重置令牌（限时 + 哈希存储） | 标准自助流程，无需管理员介入 |
| 前端框架 | **Next.js（React）** | App Router、SSR、生态成熟 |
| RAG 方案 | 文档向量化 + pgvector 检索 | 复用现有数据库，无需额外向量库 |
| 沙箱方案 | 可控开关 + **受限子进程**（本期） | 兼顾安全与灵活，落地成本低 |
| 流式协议 | SSE（非 WebSocket） | 单向流式足够，实现简单，兼容好 |
| Agent 范式 | ReAct + Function Calling | 通用性强、工程成熟、无需解析文本 |
| 工具调用协议 | OpenAI 兼容格式 | 生态通用，便于多模型适配 |
| 数据库 | PostgreSQL + pgvector | 关系+向量一体，减少组件 |
| 后端框架 | FastAPI | 异步原生，SSE 支持好 |
| 模型抽象 | 适配器模式 | 支持热切换、降级 |
| 危险操作 | 人工确认 + 沙箱开关 | 安全兜底 |

**备选方案对比**：
- **WebSocket vs SSE**：WebSocket 支持双向、可中途打断，但复杂度高。本期用 SSE + 独立 stop 接口即可满足。
- **自研循环 vs LangGraph**：LangGraph 适合复杂状态流转；本期单 Agent ReAct 自研更透明、可控、易调试。

## 9. 安全与风险控制

| 风险 | 措施 |
|------|------|
| Prompt 注入 | 工具结果与用户输入分区标记；对工具返回内容做净化 |
| 危险工具滥用 | `requires_confirmation` 机制 + 人工确认接口 + 沙箱开关 |
| 文件系统逃逸 | 用户独立沙箱根目录 + 路径规范化校验，拒绝 `../` |
| 代码执行 | **受限子进程**（本期）→ 独立容器（后续），限制资源与网络 |
| 密钥泄露 | API-Key 由管理员配置、加密存库、仅后端读取，绝不下发前端 |
| 凭证安全 | 密码加盐哈希（bcrypt/argon2）；JWT 设过期与签名校验 |
| 重置令牌 | 令牌哈希入库、一次性使用、限时过期；响应不区分邮箱是否存在（防枚举） |
| 邮件滥用 | 忘记密码 / 注册邮件接口按 IP + 邮箱限流，防轰炸与枚举 |
| 权限越权 | 管理接口校验 admin 角色；普通接口校验登录态 |
| 数据越权 | 所有查询（会话 / 消息 / 向量）强制带 `user_id` 过滤 |
| 资源滥用 | 用户级限流、单次 token 上限、最大轮次、工具超时 |

### 14.2 关键决策（已确认）

| 事项 | 决策 |
|------|------|
| LLM 供应商 | **DeepSeek**（OpenAI 兼容协议），API-Key 由管理员配置 |
| LLM 模型 | 默认 **`deepseek-flash`**，模型名可在管理后台配置切换 |
| 用户体系 | 支持**注册 / 登录 / 找回密码**，JWT 鉴权，多用户数据隔离 |
| 沙箱方案 | 提供**开关**（全局 + 会话级），本期采用**受限子进程**（后续可升级容器） |
| 前端框架 | **Next.js（React）** |
| RAG | **接入（已完成）**；上传 → 解析 → 分块 → 向量化 → `knowledge_search` 检索全链路打通，向量存 MySQL（JSON 列）+ 应用层余弦相似度，后续可换 pgvector |
| 嵌入模型 | **可插拔**：默认 `hash`（字符 n-gram 哈希，零依赖兜底，仅字面匹配）；生产建议切本地 **`BAAI/bge-small-zh-v1.5`**（sentence-transformers，离线、CPU 可跑）；亦可用 `none` 关闭 |
| `hash` 后端哈希函数 | **blake2b（64 bit）**：crc32 在短中文串上雪崩性不足，256/512 维时碰撞噪声会让无关文档得分更高 |
